# 004 — Database schema

## Goal

Створити мінімальну реляційну схему даних для повного v0.1-флоу Movie Match, щоб наступні задачі могли реалізувати кімнати, раунди й голосування через Drizzle без бізнес-логіки або seed-даних у цій задачі.

## Scope / Requirements

- Описати в `lib/db/schema.ts` мінімальні продуктові сутності: жанри, фільми, кімнати та їхні фільтри, учасники, раунди, позиції фільмів у раунді й голоси.
- Зберігати для кімнати унікальний короткий код, стан, фільтри v0.1 (`Netflix`, до двох годин, `any/new/old`, нуль або більше жанрів), час створення та `expiresAt` рівно на одну годину; саму автоматичну зміну стану після спливу часу залишити задачі 016.
- Подати скінченні доменні значення типізовано: стани кімнати й раунду, роль `host/guest`, річний фільтр і чотири семантичні значення голосу замість emoji у базі.
- Додати первинні та зовнішні ключі, потрібні `not null`, defaults, checks, unique constraints й індекси для основних інваріантів: унікальний room code; максимум один `host` і один `guest` на кімнату; унікальний номер раунду в кімнаті; позиції карток лише 1–3 без повторення позиції або фільму в одному раунді; один голос учасника за конкретну картку.
- На рівні constraints не дозволяти голосу посилатися на учасника чи картку з іншої кімнати.
- Зберігати вибрані жанри через нормалізований зв’язок кімната–жанр без дублювання. Подальша filter query має трактувати кілька жанрів через `OR`: фільм підходить, якщо має хоча б один вибраний жанр.
- Використовувати позиції фільмів у раундах як поточний список уже показаних фільмів і не допускати повторення пари кімната–фільм. Подальша дія «Restart the list» видалятиме раунди кімнати каскадно разом із їхніми позиціями та голосами, після чого нумерація раундів починатиметься з 1; кімната, учасники, фільтри та початковий строк дії залишатимуться без змін.
- Увімкнути RLS для кожної нової таблиці в `public`. Не додавати browser `SELECT`, DML grants, policies або Realtime publication у задачі 004: доступ через Supabase Data API залишається opt-in до появи конкретного read/Realtime-сценарію.
- Згенерувати й зберегти Drizzle migration разом із metadata; перевірити SQL на відповідність схемі, RLS і найменшим browser-привілеям.
- Прибрати з `docs/database.md` твердження, що продуктова схема ще порожня, та коротко описати межу доступу для нових таблиць.

## Acceptance Criteria

- `lib/db/schema.ts` експортує мінімальні таблиці, enums і relations для сутностей v0.1 та проходить TypeScript-перевірку.
- Нова migration послідовно застосовується після `0000` до чистого PostgreSQL і створює всі зовнішні ключі, unique/check constraints та індекси; повторний `db:generate` не знаходить незбережених змін.
- Схема обмежує кімнату двома ролями, не допускає повторення вибраного жанру, картки позиціями 1–3, дублікати фільму в поточному списку кімнати та повторний голос тієї самої людини за ту саму картку.
- Кожна продуктова таблиця має RLS enabled; `anon` і `authenticated` не мають `INSERT`, `UPDATE`, `DELETE` та не отримують `SELECT` у цій задачі.
- Production build, typecheck, lint і перевірка форматування проходять.
- У змінах немає seed-даних, реальних секретів, UI, route handlers або бізнес-операцій.

## Out of Scope

- Seed-каталог, початкові жанри, зовнішні movie API, імпорт або assets — задача 009.
- Створення, відновлення, приєднання, фільтрація, старт, голосування, match calculation, повторний пошук, закриття або expiration logic — задачі 005–016.
- Next.js сторінки, Server Actions, route handlers і валідація користувацьких команд.
- Supabase Realtime publication/subscriptions, browser read policies/grants і Supabase Auth.
- Фонове очищення прострочених кімнат або реалізація переходів між станами.
