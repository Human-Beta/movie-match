# Idempotency and participant sessions

Movie Match has no user accounts in v0.1, but browser operations still need stable identities across retries and reloads. This guide distinguishes the identifiers and credentials used by room creation and participant joining.

## Terminology

| Value                         | Generated by                                   | Stored in the browser                           | Stored in PostgreSQL                    | Purpose                                                  |
| ----------------------------- | ---------------------------------------------- | ----------------------------------------------- | --------------------------------------- | -------------------------------------------------------- |
| Room code                     | Server                                         | TV `localStorage`                               | `rooms.code`                            | Public room locator; not a credential                    |
| `creationRequestId`           | TV browser with `crypto.randomUUID()`          | TV `localStorage` until a terminal result       | Raw UUID in `rooms.creation_request_id` | Idempotent room creation; not a credential               |
| Raw participant access token  | Server from 32 cryptographically random bytes  | Room-scoped `HttpOnly` cookie                   | Never                                   | Join idempotency and participant session credential      |
| Participant access-token hash | Server with SHA-256                            | Never                                           | `participants.access_token_hash`        | Finds the participant without storing the raw credential |
| Game command request ID       | Host browser with `crypto.randomUUID()`        | Host tab `sessionStorage` until terminal        | `room_game_commands.request_id`         | Idempotent start, list restart, search-again, and close  |
| Ballot request ID             | Participant browser with `crypto.randomUUID()` | Participant tab `sessionStorage` until terminal | `round_ballots.request_id`              | Idempotent complete private ballot submission            |

The participant token is an opaque bearer credential, not a JWT. Supabase Auth is not part of this flow.

## Idempotent TV room creation

Before the TV requests a room, it reads a pending `creationRequestId` from `localStorage` or creates and persists a UUID. The server validates the UUID and creates the room with a unique `rooms.creation_request_id`.

If the server commits the room but its response is lost, the TV retries with the same request ID. The unique constraint and repository lookup return the original room instead of creating a duplicate. The TV clears the request ID only after it receives a terminal result: after it safely stores the returned room code, or when the server explicitly says that the request ID must be replaced.

The request ID is not secret and does not authorize access to the room.

## Participant join preparation

Opening `/join/{roomCode}` does not immediately create a participant. A server action first validates the room code and confirms that the room exists, is waiting, and has not expired.

For an eligible room, the server reuses a valid pending join token or generates 32 random bytes and Base64URL-encodes them as a 43-character token. The raw token is written only to `movie-match.join-request.{ROOM_CODE}` with these attributes:

- `HttpOnly`, so browser JavaScript cannot read it;
- `SameSite=Lax`;
- `Secure` in production;
- `Path=/join`;
- expiration equal to the room expiration.

The raw token is never placed in a URL, browser-readable storage, an action response, or a server log.

## Successful join and session promotion

On submit, the server validates the name and room code, reads the pending join token, hashes it with SHA-256, and runs the join inside a room-locking transaction.

The transaction resolves identities in this order:

1. A valid existing participant cookie restores its participant.
2. A participant with the pending join-token hash is treated as a retry of an earlier committed join.
3. Otherwise, a waiting room assigns the first free role and stores a new participant with only the token hash.

For a new or retried participant session, the same raw token is written to `movie-match.participant.{ROOM_CODE}`. It is not replaced with a separately generated session token. The pending join cookie is then expired after the server produces a terminal `joined`, `full`, or `unavailable` result. Unexpected failures leave the pending token available for a safe retry.

## Lost-response recovery

Assume the pending raw token is `T`:

1. The join transaction stores `SHA256(T)` and commits the participant.
2. The response containing the participant cookie is lost.
3. The browser still has the pending join cookie containing `T`.
4. A retry hashes `T`, finds the committed participant, and returns the same identity without consuming another room slot.
5. The response reissues `T` as the participant cookie and expires the pending join cookie.

This is why the token is generated before the insert and reused across retries.

## Reload and future authorization

On reload, server code reads the room-specific participant cookie, validates its format, hashes it, and looks up the participant by the stored hash. Restoration is allowed only while the room is not closed or expired. A known participant may be restored in later active room states, while a new participant may join only a waiting room.

Future host and voting commands must repeat server-side room, participant, and role checks. Possession of the cookie identifies a participant but does not by itself authorize every operation.

Participant cookies expire no later than the room. The database stores only unique hashes, and public action state is rebuilt explicitly so raw credentials and internal participant identifiers do not reach the client.

## Host filter saves

The host form stores a UUID and the exact pending filter values in the current tab's `sessionStorage`, under `movie-match.filter-save.{ROOM_CODE}`, before calling the save Server Action. This non-secret request ID is separate from the participant credential, which remains in its existing HttpOnly cookie. Tab-scoped storage survives reload while keeping independent tabs' pending edits separate.

The server validates the room code, UUID, strict boolean fields, year enum, and positive integer genre IDs; it deduplicates and sorts genre IDs before hashing a fixed-order allowlist of the filter values. Under a `rooms` row lock it verifies the room-scoped host credential and an unexpired `waiting` state, checks that genres exist, replaces changed filters, and inserts a `room_filter_saves` receipt atomically. Saving an unchanged normalized contract writes only its idempotency receipt, so it does not update room data or trigger a public-state transition.

A repeated request with the same payload returns the currently saved filters. It never reapplies its original values, even when another save has committed since then. Reusing the ID with different values returns a terminal conflict. New saves must use new IDs. Future start-game commands must lock the same room row so the game cannot start with a partially updated filter set.

A transport or unexpected server failure leaves the pending request intact and locks editing until the host explicitly retries. Reload restores this pending payload and offers the same retry. A confirmed saved, validation-error, conflict, or unavailable response clears only the matching pending ID. If storage cannot persist the request, no mutation is sent. A read-only initial Server Action loads the authorized filters and genres; it sets no cookies and depends only on the room code and an explicit retry counter. Participant snapshot updates do not reload the form or replace its draft.

The filter contract lives in `lib/room-filters/room-filter-values.ts`: Netflix requires the manually maintained availability flag; runtime is strictly below 120 minutes; new releases are after 2010 and old releases include 2010. Categories combine with AND, selected genres with OR, and an empty genre set means any genre. Task 010 consumes these persisted values when generating a round.

## Game start and list restart

Before the host sends a start or restart command, the current tab stores a UUID under the room- and command-scoped `sessionStorage` key `movie-match.game-command.{COMMAND}.{ROOM_CODE}`. The UUID is non-secret; the existing HttpOnly participant cookie remains the only participant credential. If browser storage is unavailable or corrupt, the UI does not send the mutation.

The server validates only the normalized room code and UUID from the browser. It derives the command kind from the invoked Server Action, hashes a canonical allowlist containing that command and room code, and performs authorization and generation inside a Drizzle transaction that locks the `rooms` row. It rechecks the room-scoped host credential, expiration, state, persisted participant membership, and current saved filters. Movie IDs, roles, filters, and generated order are never accepted from the client.

`room_game_commands` stores the request ID, command, payload hash, filter-contract hash, and committed `started`, `catalog_insufficient`, or `list_exhausted` outcome. `started` and `list_exhausted` commit their corresponding room transition; `catalog_insufficient` commits only the idempotency receipt and remains host-local. A matching retry returns that receipt even after later game-state changes; reusing the key for another command conflicts. The browser clears only the matching request after a terminal response. Transport and unexpected failures retain it for explicit retry, while authoritative snapshot refresh also recovers a committed round whose response was lost.

Start and filter-save commands serialize on the same room row, so a generated round uses one complete persisted filter set. When fewer than three unseen candidates remain, start compares the complete filtered catalog before committing: `catalog_insufficient` does not offer a list restart and does not alter the room snapshot, while `list_exhausted` does transition the room. A catalog-insufficient receipt for the current filter-contract hash disables another start in the host UI until a different contract is saved; guest and TV receive no update. Restart is server-authorized only from `list_exhausted`, verifies the full filtered catalog contains three candidates, then deletes only that room's round history through cascades and creates round 1 in the same transaction. A catalog-insufficient result never deletes history, and replaying a successful restart cannot delete the newly created round.

## Post-match search and close

Before a host sends either post-match command, the current tab stores one object containing the command (`search_again` or `close`) and a UUID under `movie-match.post-match-command.{ROOM_CODE}` in `sessionStorage`. It persists before the Server Action call and is cleared only after a terminal response. A transport failure retains the same command and request ID for an explicit retry; the mounted UI prevents selecting the other command while that request remains pending.

The Server Action accepts only the normalized room code and UUID. Under the existing room row lock, it rechecks the non-expired participant session and persisted `host` role before looking up the idempotency receipt. The receipt's payload hash includes the command and room code, so a key used by one post-match command cannot authorize the other command. A matching replay returns its committed outcome even after the room has changed; an unmatched request cannot reopen a closed room.

`search_again` additionally requires a `matched` room whose current matched round has a persisted selected movie. It reads the saved filters, excludes every `round_movies` entry in the room history, and atomically either creates the next three-position voting round and moves the room to `playing`, or moves the room to `exhausted` when fewer than three unseen candidates remain. It does not delete historical rounds, votes, or the selected movie. `close` requires the matched room state and atomically writes `closed` without deleting room history. Both committed transitions emit only the existing payload-free room invalidation; missed delivery is recovered by the authoritative matched-state fallback and reload.

## Private ballot submission

Before a participant submits a ballot, the phone stores one UUID and its full three movie-ID/value pairs under `movie-match.ballot.{ROOM_CODE}.{ROUND_ID}` in `sessionStorage`. This key and payload are non-secret; the room-scoped HttpOnly participant cookie remains the only credential. The pending entry is persisted before any mutation, is retained after a transport or unexpected action failure, and is cleared only after a terminal response or an authoritative private snapshot confirms that the ballot is already submitted.

The Server Action validates the strict payload, derives the authenticated participant from the participant cookie, and hashes a canonical allowlist of the normalized room code, round ID, and movie-ID/value pairs sorted by movie ID. Under the room row lock it checks room expiration and `playing` state, participant membership, the current `voting` round, and exact membership of all three persisted round movies. It then inserts three `votes` rows and one `round_ballots` completion marker in the same Drizzle transaction.

The completion marker's primary key makes the ballot immutable, while its `(room_id, participant_id, request_id)` unique constraint makes each participant's request ID single-use across all of that room's rounds. A retry with the same request ID, stored round ID, and canonical payload returns the existing completion even after a response loss or later round transition; the same request ID with altered pairs or another round conflicts. The same UUID remains independent for another participant or room. An old request with no matching completion cannot write into a later round because its supplied round ID must still be the currently locked voting round. Failed writes roll back all three votes and the marker together.

The TV's snapshot contains only the non-sensitive submitted-ballot count and readiness flag. A phone snapshot is separately authorized and explicitly allowlists only that participant's submitted state and its own values; it cannot serialize the other participant's values, any receipt, request ID, token hash, or credential. Room Broadcast remains a payload-free invalidation hint. Each mounted screen uses one channel and a bounded authoritative active-voting fallback poll so missed or forged messages can change only when a server snapshot confirms new progress.
