# Agent workflow roadmap

This roadmap preserves the agreed workflow tasks and decisions across chats. Start each WF task in a separate chat by its ID; a fork is optional. The repository is the handoff source, so update this file when an agreed decision changes instead of relying on conversation history.

This is planned work, not active agent instructions. `AGENTS.md`, `docs/openspec.md`, and `docs/review.md` remain the current workflow until a task explicitly updates them. Implementation checklists belong in the selected OpenSpec change, not in this roadmap.

## Agreed workflow decisions

- Write permanent documentation, specifications, plans, new tickets, and agent guidance in English. Chat language is the user's choice; preserve legacy Ukrainian task history.
- The starting model roles are Sol for coordination, discovery, planning, architecture, and independent review; Luna for bounded implementation and unit tests; Luna for QA with escalation to Sol for difficult analysis. Evaluate this policy on completed work rather than assuming the cheaper model always reduces total cost.
- The human reviews expected behavior, examples, constraints, and material product decisions before implementation, then accepts the running result or preview and the verification report. Routine acceptance must not require understanding the code diff once WF-06 is implemented.
- Planning includes inspecting existing code, tests, and callers, identifying concrete reuse, and explaining any new module or abstraction. Keep components and modules cohesive without speculative wrappers.
- Prefer unit tests of business rules and state transitions using real collaborating objects. Use boundary doubles only where necessary. Database transactions, constraints, locks, and RLS need focused Postgres integration tests; cookies, effects, reconnects, and multi-screen behavior need a small set of browser scenarios.
- Independent QA derives checks from acceptance criteria and observable behavior, rather than merely adding tests that mirror the implementation. Review includes correctness, scope, architecture, tests, and documentation.
- Automatically fix clear findings within the approved scope, then repeat relevant checks and review. After two unsuccessful correction cycles, report the concrete blocker or escalate to the stronger model. Material product decisions and disputed findings go to the user.
- Templates combine one shared core with independent tool and stack profiles. GitHub template repositories do not inherit another repository automatically: generated stack templates already contain a recorded core version. Core updates arrive through reviewed PRs; newly created projects receive the template's current contents. Existing projects remain independent and update explicitly.
- Reuse the existing Vercel production-release workflow. A deployment request authorizes that release action; verify the selected commit and checks. A permanent `production` branch is not required by default. Release tags and other release rules remain governed by `AGENTS.md`.

## WF-06 request routing

The user describes the desired outcome in ordinary language and does not need to remember OpenSpec skill names. Encode this policy in persistent instructions and test representative requests when implementing WF-06.

| Request                                                                                | Route                                                                                                                                             |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| New feature/page, changed business rules, or a substantial change across related areas | Use OpenSpec planning, get specification/plan acceptance, then implement.                                                                         |
| Small bug with understood cause and existing expected behavior                         | Fix directly, add an appropriate regression test where useful, and run relevant checks.                                                           |
| Local text, style, or obvious mechanical correction                                    | Change directly and run proportionate checks.                                                                                                     |
| Unclear report such as “this works incorrectly”                                        | Investigate first; choose direct work or OpenSpec once the cause and intended behavior are understood. Ask only for unresolved product decisions. |
| Work covered by an active OpenSpec change                                              | Continue that change; revise its artifacts when necessary instead of creating a duplicate.                                                        |

Announce the route briefly, for example “This is a local bug; I will fix it directly” or “This changes behavior; I will prepare an OpenSpec proposal first.” Investigations need not always invoke a separate explore skill. OpenSpec is not mandatory for every edit, and installing skills alone does not implement this routing or the full orchestration loop.
